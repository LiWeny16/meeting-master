# Realtime ASR

Meeting recording can stream both WASAPI sources to a configurable WebSocket recognizer while preserving the existing WAV capture path. The microphone and system-output sources use separate WebSocket sessions, each labeled with the meeting, recording session, source, and stable turn ID. PCM is mono, 16 kHz, signed 16-bit little-endian. The recording pipeline still writes its 48 kHz stereo files and 16 kHz ASR WAV files independently of recognizer availability.

Select **Local WebSocket ASR** in ASR settings and configure its WebSocket URL and bearer token. The default URL is `ws://192.168.0.200:8092/v1/asr/stream`; deployments can change it. The token is stored using the app's protected credential storage and sent only in the `Authorization: Bearer …` handshake header. It is not logged or included in stream status messages. The provider is a remote WebSocket connection; downloading a model in the ASR model manager does not make this provider run inference on this PC.

The client sends a JSON `start` message with the turn ID, `sample_rate: 16000`, `channels: 1`, and `encoding: "pcm_s16le"`, followed by binary PCM chunks and a JSON `end` message with the number of audio frames sent. Turns start after voiced audio, include up to 160 ms of pre-roll, end after about 700 ms of quiet, and are capped at 15 seconds. The server returns cumulative `partial` updates and a `final`; the final must report a `frame_end` equal to the number of samples sent. Missing, regressing, or out-of-range frame positions fail that source's ASR stream rather than assigning unsupported timestamps.

Partial `transcript-update` events replace the current text for their stable segment ID. A final event replaces that same segment and is appended to `transcript.jsonl` with a flush and durable sync. Transcript list and search APIs return only saved final segments. Frame offsets are converted to timestamps from the recording session start. `asr-stream-status` reports `connecting`, `streaming`, `stopped`, or `error` per meeting, session, and source. Its `latencyMs` is an approximate recognizer processing delay correlated to the server's `frame_end` and outbound chunk timestamps; it is not a full microphone-to-display latency measurement.

The PCM queue is bounded. If the recognizer cannot keep up, the affected ASR source reports an error and stops streaming; audio capture and WAV persistence continue. Stopping a recording sends any resampler remainder, ends active turns, and waits up to eight seconds for final transcripts before completing capture. Connectivity errors do not turn an unconfigured or unavailable recognizer into a success state.

The provider test performs an authenticated WebSocket handshake, sends a short digital-silence turn, ends it, and requires a final with the expected frame count. It is a connectivity and protocol check, not an accuracy test.
